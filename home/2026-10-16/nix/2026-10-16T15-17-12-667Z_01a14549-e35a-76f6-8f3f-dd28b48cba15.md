# Learning Nix for Experienced Programmers (Source-Code Approach)

As an experienced programmer with access to the Nix source code, you have a unique advantage: you can learn Nix by understanding its architecture rather than just memorizing its commands. This roadmap is designed to bridge the gap between the **Nix Engine** (the software you have the source for) and the **Nix Language** (the DSL you will use).

## 1. Distinguish the Engine from the Language
Before diving in, understand the two layers of Nix:
*   **The Engine (Source Code):** The implementation (C/Rust/etc.) that handles file locking, the Nix store, networking, parsing, and evaluation.
*   **The Language (Nix Expressions):** The declarative DSL used to define build instructions, configurations, and environments.

## 2. The Architecture Walkthrough
Instead of reading documentation, explore the project structure. Identify these core components in the source:

*   **`nix-expr`**: Locate the evaluation engine. Study how expressions are parsed into Abstract Syntax Trees (ASTs) and how they are reduced to values.
*   **The Store**: Find the logic for the `/nix/store`. Analyze how it handles atomicity and how it implements content-addressable storage.
*   **Derivations**: This is the fundamental unit of Nix. Find the data structures that represent a "build instruction." A derivation is essentially a pure function: `Inputs -> Outputs`.
*   **Fetchers**: Examine how Nix handles remote dependencies. This reveals how Nix maintains reproducibility by verifying external data.

## 3. Trace-Driven Learning
The fastest way for a developer to learn a new system is to trace a single execution path.

**Exercise:** Run `nix build --eval -E '(import <nixpkgs> {}).hello'` and trace it:
1.  Find the entry point of the `nix build` command in the source.
2.  Follow the code as it calls the **parser** to turn the string into an AST.
3.  Follow the **evaluator** as it resolves `<nixpkgs>` (this will lead you to Flake/Channel logic).
4.  Observe how it produces a **Store Path** as the final result.

## 4. Study the "Standard Library" (nixpkgs)
Once you understand the engine, you need to learn the "idioms" of the language.
*   **Analyze `nixpkgs`**: This is the de facto standard library. By reading how common packages (like `python`, `gcc`, or `nodejs`) are defined, you will learn the standard patterns for handling dependencies, build flags, and environment isolation.

## 5. "Read-Modify-Run" Mastery
Use your access to the source to solidify your mental model:
*   **Inject Logging**: Add print statements or loggers to the evaluation engine to see what happens during a build.
*   **Small Hacks**: Modify a small behavior in the tool, recompile it, and run it. 
*   **Debug**: When you encounter a confusing Nix error, look for the corresponding error handling in the source code to see exactly what part of the evaluation failed.

## Summary Roadmap
1.  **Scan** the project tree for Parser, Evaluator, and Store modules.
2.  **Write** a simple `.nix` file and run `nix build`.
3.  **Trace** that specific execution through the source code.
4.  **Read** `nixpkgs` to learn the "best practices" of the DSL.
5.  **Debug** the tool itself to understand the internal mechanics.

      │ └── baz
      │   ├── blah
      │   │   └── file.txt

## Derivation output selection

Derivations can have multiple outputs, each corresponding
to a different store path. For instance, a package can have
a bin output that contains programs, and a dev output that
provides development artifacts like C/C++ header files. The
outputs on which nix commands operate are determined as
follows:

  · You can explicitly specify the desired outputs using
    the syntax installable^output1,...,outputN — that is,
    a caret followed immediately by a comma-separated list
    of derivation outputs to select. For installables
    specified as Flake output attributes or Store paths,
    the output is specified in the same argument:
    
    For example, you can obtain the dev and static outputs
    of the glibc package:
    
      │ # nix build 'nixpkgs#glibc^dev,static'
      │ # ls ./result-dev/include/ ./result-static/lib/
      │ …
    
    and likewise, using a store path to a "drv" file to
    specify the derivation:
    
      │ # nix build '/nix/store/fpq78s2h8ffh66v2iy0q1838mhff06y8-glibc-2.33-78.drv^dev,static'
      │ …
    
    For --expr and -f/--file, the derivation output is
    specified as part of the attribute path:
    
      │ $ nix build -f '<nixpkgs>' 'glibc^dev,static'
      │ $ nix build --impure --expr 'import <nixpkgs> { }' 'glibc^dev,static'
    
    This syntax is the same even if the actual attribute
    path is empty:
    
      │ $ nix build --impure --expr 'let pkgs = import <nixpkgs> { }; in pkgs.glibc' '^dev,static'

  · You can also specify that all outputs should be used
    using the syntax installable^*. For example, the
    following shows the size of all outputs of the glibc
    package in the binary cache:
    
      │ # nix path-info --closure-size --eval-store auto --store https://cache.nixos.org 'nixpkgs#glibc^*'
      │ /nix/store/i2fn2mjgihz960bwa7ldab5ra5fhxznh-glibc-2.33-123                 33208200
      │ /nix/store/n2wnn3i47w6dbylh64hdjzgd5rrprdn8-glibc-2.33-123-bin             36142896
      │ /nix/store/v7dyz518sbkzl8x2a1sgk1lwsfd3d6gm-glibc-2.33-123-debug          155787312
      │ /nix/store/z4hv6ybyinqw9a3dwyl5k66a91aggylj-glibc-2.33-123-static          42488328
      │ /nix/store/lrjirf0j1rjnvif6amyp9pfcqr2km385-glibc-2.33-123-dev             44200560
    
    and likewise, using a store path to a "drv" file to
    specify the derivation:
    
      │ # nix path-info --closure-size '/nix/store/fpq78s2h8ffh66v2iy0q1838mhff06y8-glibc-2.33-78.drv^*'
      │ …

  · If you didn't specify the desired outputs, but the
    derivation has an attribute meta.outputsToInstall, Nix
    will use those outputs. For example, since the package 
    nixpkgs#libxml2 has this attribute:
    
      │ # nix eval 'nixpkgs#libxml2.meta.outputsToInstall'

    only those two outputs by default.
    
    Note that a store derivation doesn't have any
    attributes like meta, and thus this case doesn't apply
    to it.

  · Otherwise, Nix will use all outputs of the derivation.

Shebang interpreter

The nix command can be used as a #! interpreter. Arguments
to Nix can be passed on subsequent lines in the script.

Verbatim strings may be passed in double backtick (``)
quotes. <!-- that's markdown for two backticks in inline
code. --> Sequences of n backticks of 3 or longer are
parsed as n-1 literal backticks. A single space before the
closing `` is ignored if present.

--file and --expr resolve relative paths based on the
script location.

Examples:

  │ #!/usr/bin/env nix
  │ #! nix shell --file ``<nixpkgs>`` hello cowsay --command bash
  │ 
  │ hello | cowsay

or with flakes:

  │ #!/usr/bin/env nix
  │ #! nix shell nixpkgs#bash nixpkgs#hello nixpkgs#cowsay --command bash
  │ 
  │ hello | cowsay

or with an expression:

  │ #! /usr/bin/env nix
  │ #! nix shell --impure --expr ``
  │ #! nix with (import (builtins.getFlake "nixpkgs") {});
  │ #! nix terraform.withPlugins (plugins: [ plugins.openstack ])
  │ #! nix ``
  │ #! nix --command bash
  │ 
  │ terraform "$@"

or with cascading interpreters. Note that the #! nix lines
don't need to follow after the first line, to accommodate
other interpreters.

  │ #!/usr/bin/env nix
  │ //! ```cargo
  │ //! [dependencies]
  │ //! time = "0.1.25"
  │ //! ```
  │ /*
  │ #!nix shell nixpkgs#rustc nixpkgs#rust-script nixpkgs#cargo --command rust-script
  │ */
  │ fn main() {
  │     for argument in std::env::args().skip(1) {
  │         println!("{}", argument);
  │     };
  │     println!("{}", std::env::var("HOME").expect(""));
  │     println!("{}", time::now().rfc822z());
  │ }
  │ // vim: ft=rust

This plan is designed for an experienced programmer who prefers understanding **mechanics over syntax**. Since you are limited to `cat -n` and the provided `nix` binary, we will use a "reverse-engineering" approach: starting from the output of the tool and working backward into the source code.

### 30-Minute "Source-First" Learning Plan

#### Phase 1: Mapping the Territory (5 Minutes)
*Goal: Identify the core modules mentioned in the README.*

1.  **Directory Recon:** Run `ls -R` (or `find .`) to get a high-level view of the project structure.
2.  **Locate Core Modules:** Use `ls` and `grep` (if available) or just browse the tree to find the directories corresponding to:
    *   **`nix-expr`**: Look for keywords like `eval`, `ast`, or `parse`.
    *   **`store`**: Look for `/nix/store` logic or `content-addressable`.
    *   **`derivation`**: Look for `drv` or `build` logic.
3.  **Identify the Language:** Determine if it's C, Rust, or another language to know what to look for (e.g., `main.rs`, `main.c`, `lib.py`).

#### Phase 2: The "Easy Win" Trace (5 Minutes)
*Goal: Confirm you can link a CLI output to a specific line of source code.*

1.  **Execute:** `nix run /home/2026-10/nix/nix -- --version`
2.  **Observe:** Note the output: `nix (Nix) 2.36.0pre20261016_38856d0`.
3.  **Trace:** Use `cat -n` to search the source code for the string `2.36.0` or the word `version`.
4.  **Identify:** Find the exact file and line number where the version string is defined. This establishes the "Trace" workflow.

#### Phase 3: The Evaluation Trace (15 Minutes)
*Goal: Understand how Nix turns a string into a value.*

1.  **Execute:** `nix run /home/2026-10/nix/nix -- --eval -E '1 + 1'`
2.  **Observe:** The output will be `2`.
3.  **Trace the Entry Point:** 
    *   Find the `main` function in the source. 
    *   Trace how it handles the `--eval` flag.
4.  **Trace the Parser:** 
    *   Look for the code that takes the string `'1 + 1'` and converts it into an Internal Representation (AST).
    *   Search for functions like `parse_expression` or `tokenize`.
5.  **Trace the Evaluator:**
    *   Follow the AST into the evaluation engine. 
    *   Identify the logic that performs the addition. This is the heart of `nix-expr`.

#### Phase 4: Synthesis & Architecture Wrap-up (5 Minutes)
*Goal: Connect the "Engine" to the "Language".*

1.  **Compare:** Look at the `nix --help` output again.
2.  **Relate:** Pick one subcommand (e.g., `nix build`). 
3.  **Mental Map:** Briefly locate where in the source code that subcommand's logic lives. 
    *   *Example:* "I see `nix build` in the help. I found the `build` command in `src/commands/build.rs` (or equivalent), which calls the `derivation` module I saw in Phase 1."
4.  **Final Summary:** You have now moved from "Running a command" $\rightarrow$ "Finding the output in source" $\rightarrow$ "Tracing the logic flow."

---

### Pro-Tips for this Session:
*   **Follow the Data:** If you find a function that takes a `String` and returns a `Result<Value>`, that is your Parser. If it takes a `Value` and returns a `Value`, that's your Evaluator.
*   **Ignore the Noise:** Don't try to understand every line. Only follow the path of the `1 + 1` execution.
*   **Stay in the Source:** If you get confused by a Nix expression, go back to the source code. The source code is the "source of truth" for how the engine interprets that expression.

# Learning Nix for Experienced Programmers (Source-Code Approach)

As an experienced programmer with access to the Nix source code, you have a unique advantage: you can learn Nix by understanding its architecture rather than just memorizing its commands. This roadmap is designed to bridge the gap between the **Nix Engine** (the software you have the source for) and the **Nix Language** (the DSL you will use).

## 1. Distinguish the Engine from the Language
Before diving in, understand the two layers of Nix:
*   **The Engine (Source Code):** The implementation (C/Rust/etc.) that handles file locking, the Nix store, networking, parsing, and evaluation.
*   **The Language (Nix Expressions):** The declarative DSL used to define build instructions, configurations, and environments.

## 2. The Architecture Walkthrough
Instead of reading documentation, explore the project structure. Identify these core components in the source:

*   **`nix-expr`**: Locate the evaluation engine. Study how expressions are parsed into Abstract Syntax Trees (ASTs) and how they are reduced to values.
*   **The Store**: Find the logic for the `/nix/store`. Analyze how it handles atomicity and how it implements content-addressable storage.
*   **Derivations**: This is the fundamental unit of Nix. Find the data structures that represent a "build instruction." A derivation is essentially a pure function: `Inputs -> Outputs`.
*   **Fetchers**: Examine how Nix handles remote dependencies. This reveals how Nix maintains reproducibility by verifying external data.

## 3. Trace-Driven Learning
The fastest way for a developer to learn a new system is to trace a single execution path.

**Exercise:** Run `nix build --eval -E '(import <nixpkgs> {}).hello'` and trace it:
1.  Find the entry point of the `nix build` command in the source.
2.  Follow the code as it calls the **parser** to turn the string into an AST.
3.  Follow the **evaluator** as it resolves `<nixpkgs>` (this will lead you to Flake/Channel logic).
4.  Observe how it produces a **Store Path** as the final result.

## 4. Study the "Standard Library" (nixpkgs)
Once you understand the engine, you need to learn the "idioms" of the language.
*   **Analyze `nixpkgs`**: This is the de facto standard library. By reading how common packages (like `python`, `gcc`, or `nodejs`) are defined, you will learn the standard patterns for handling dependencies, build flags, and environment isolation.

## 5. "Read-Modify-Run" Mastery
Use your access to the source to solidify your mental model:
*   **Inject Logging**: Add print statements or loggers to the evaluation engine to see what happens during a build.
*   **Small Hacks**: Modify a small behavior in the tool, recompile it, and run it. 
*   **Debug**: When you encounter a confusing Nix error, look for the corresponding error handling in the source code to see exactly what part of the evaluation failed.

## Summary Roadmap
1.  **Scan** the project tree for Parser, Evaluator, and Store modules.
2.  **Write** a simple `.nix` file and run `nix build`.
3.  **Trace** that specific execution through the source code.
4.  **Read** `nixpkgs` to learn the "best practices" of the DSL.
5.  **Debug** the tool itself to understand the internal mechanics.
