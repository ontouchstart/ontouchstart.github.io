## The Nix-to-Scratch Workflow

1.  **Build the Closure:** Use `nix build` to create your Go binary. Nix ensures that the binary and every single library it depends on are stored in the `/nix/store` with unique hashes.
2.  **Calculate the Minimal Set:** Use the command `nix-store -qR $(nix-build -A your-app)` to generate a list of every dependency required to run that specific binary. This is the "closure."
3.  **Construct the Scratch Image:** Create a Dockerfile that starts `FROM scratch`. This creates an image with zero bytes of overhead—no shell, no package manager, and no OS vulnerabilities.
4.  **Copy the Store:** Use the `COPY` command in your Dockerfile to move only the paths identified in the closure from the host's `/nix/store` into the image's `/nix/store`.
5.  **Set the Entrypoint:** Point the `ENTRYPOINT` directly to the binary's location within the `/nix/store`.

## Technical Advantages
This approach solves the "it works on my machine" problem more effectively than standard Dockerfiles because the environment is pinned at the binary level, not the image level.

*   **Absolute Minimality:** By using `FROM scratch`, the image contains nothing but your binary and its direct dependencies. This reduces the attack surface and keeps image sizes extremely small, which is critical for fast scaling of Temporal workers.
*   **Build Speed:** Nix caches build artifacts more aggressively and accurately than Docker layers. If a dependency hasn't changed, Nix won't rebuild it, leading to faster CI pipelines.
*   **Standard Compatibility:** Because the final output is a standard Docker image, it remains fully compatible with Kubernetes, AWS ECS, and other container orchestrators without requiring Nix to be installed on the production servers.

### `.github/workflows/ci.yml`

```yaml
name: Build and Push Temporal Worker

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Install Nix
        uses: cachix/install-nix-action@v22
        with:
          # Ensures the runner has Nix installed for the build process
          extra_nix_config: |
            experimental-features = nix-command flakes

      - name: Build Worker Binary
        run: |
          # Build the worker defined in the flake (assuming attribute name is 'worker')
          nix build .#worker
          echo "BINARY_PATH=$(readlink -f result)" >> $GITHUB_ENV

      - name: Generate Closure List
        run: |
          # Find every dependency required by the binary
          # We save this to a file to iterate over it during the Docker build
          nix-store -qR ${{ env.BINARY_PATH }} > closure.txt

      - name: Generate Dynamic Dockerfile
        run: |
          # Create a Dockerfile that starts FROM scratch
          # and copies only the identified closure paths
          echo "FROM scratch" > Dockerfile
          
          # Convert the closure.txt list into a series of COPY commands
          # Note: We copy from the host's /nix/store into the image's /nix/store
          while read -r path; do
            # Docker COPY requires the source to be within the build context
            # We will handle this by copying the store to a local folder first
            echo "COPY $path $path" >> Dockerfile
          done < closure.txt
          
          # Set the entrypoint to the binary's specific nix-store path
          echo "ENTRYPOINT [\"${{ env.BINARY_PATH }}\"]" >> Dockerfile

      - name: Prepare Build Context
        run: |
          # Docker cannot COPY files from outside its context (like /nix/store).
          # We create a local 'context' directory and symlink/copy the closure.
          mkdir -p build_context
          while read -r path; do
            # Use cp -a to preserve structure and permissions
            mkdir -p "build_context$path"
            cp -a "$path" "build_context$path"
          done < closure.txt
          # Move the Dockerfile into the context
          mv Dockerfile build_context/

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and Push Docker Image
        uses: docker/build-push-action@v5
        with:
          context: ./build_context
          push: true
          tags: ghcr.io/${{ github.repository }}/temporal-worker:latest
```

```bash
  "

# 3. Dynamic Dockerfile Generation
BINARY_PATH=$(cat .binary_path)
echo "📝 Generating minimalist Dockerfile..."
cat <<EOF > Dockerfile
FROM scratch
# Copy the mirrored Nix store from the dist folder to the root
COPY $DIST_DIR /
# Set the entrypoint to the absolute Nix store path of the binary
ENTRYPOINT ["$BINARY_PATH"]
EOF

# 4. Final Image Assembly
echo "🏗️ Building scratch image..."
docker build -t "$IMAGE_NAME" .

echo "✅ Successfully built $IMAGE_NAME"
echo "Binary path: $BINARY_PATH"
```

### Why this is the ideal pattern:
1.  **Single Source of Truth:** The `build.sh` script is the only place where the build process is defined. If you change how the closure is handled, it updates for both you and the CI.
2.  **Zero Host Setup:** You don't need Nix on your Mac, and you don't need it on the GHA runner. Only Docker is required.
3.  **Mirroring Strategy:** By mirroring the `/nix/store` into `./dist`, we satisfy Docker's requirement that all files being `COPY`ed must exist within the build context.
4.  **Pure Scratch:** The final image remains a `scratch` image—no shell, no OS, just the Go binary and its hashed dependencies. This ensures absolute environmental determinism for your Temporal workflows.
