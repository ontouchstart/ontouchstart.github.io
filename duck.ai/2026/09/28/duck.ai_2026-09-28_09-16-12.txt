The React codebase is a large monorepo that separates the core API from the logic used to update the UI. Instead of one monolithic engine, React is split into several packages that handle specific responsibilities, allowing the core logic to be reused across different platforms like the web (react-dom) and mobile (react-native).

## Monorepo Organization

The majority of the logic resides in the `packages` directory. Understanding the codebase requires knowing which package handles which part of the lifecycle:

*   `packages/react`: This contains the public API that developers interact with, such as `useState`, `useEffect`, and `createElement`. It is intentionally lightweight because it mostly defines the "what" rather than the "how."
*   `packages/react-reconciler`: This is the brain of React. It contains the diffing algorithm and the Fiber architecture. It manages the tree of components and decides which parts of the UI need to change without being tied to any specific platform.
*   `packages/react-dom`: This is the glue between the reconciler and the browser's DOM. It handles the actual creation of HTML elements and the mapping of React's internal instructions to browser APIs.
*   `packages/scheduler`: This is a low-level utility that manages task prioritization. It ensures that urgent updates (like typing in an input) happen before non-urgent ones (like rendering a large list in the background).

## The Core Engine: Fiber

The most critical part of the codebase is the Fiber architecture, found primarily within `react-reconciler`. Before Fiber, React used a recursive "stack" reconciler that could lock the main thread during large updates. Fiber changed this by turning the render process into a linked list of "work units" called Fibers.

A Fiber is essentially a JavaScript object that represents a component and its state. Because they are structured as a linked list (with `child`, `sibling`, and `return` pointers), React can pause work, yield control back to the browser to handle a user event, and then resume exactly where it left off. This is what enables Concurrent Mode and Transitions.

## The Render and Commit Pipeline

The codebase implements a two-phase system to update the UI:

The Render Phase is asynchronous and interruptible. The reconciler traverses the Fiber tree and marks which components need to be added, updated, or deleted. This creates a "work-in-progress" tree. Because this phase doesn't change the actual DOM, React can throw away this work or pause it if a higher-priority update arrives.

The Commit Phase is synchronous and uninterruptible. Once the work-in-progress tree is complete, React enters the commit phase. This is where `react-dom` takes the list of changes (called "effects") and applies them to the real DOM in one quick burst to avoid visual glitches or "flickering."

## Hook Implementation Details

Hooks are not magic functions but are implemented as a linked list attached to the Fiber node. When you call `useState` or `useEffect`, React looks at the `memoizedState` property of the current Fiber.

The first time a component renders, React creates a linked list of hook objects. On subsequent renders, React simply iterates through that same list in the exact same order. This is why the "Rules of Hooks" exist: if you put a hook inside a conditional statement, the order of the list changes, and React will associate the state of one hook with the wrong variable.

## Navigation Tips for the Repo

If you are exploring the code on GitHub, start with `packages/react-reconciler/src/ReactFiberWorkLoop.js`. This file is the heart of the library and contains the loop that drives the entire rendering process. From there, you can follow the logic into `ReactFiberBeginWork.js` to see how React decides to update a component, and `ReactFiberCommitWork.js` to see how those updates are finally pushed to the screen.

Using Nix for this series is a great choice because these projects vary in their dependencies—some use raw JavaScript, others require the actual `react-reconciler` package, and some might need specific Node.js versions.

The most efficient way to handle a series of related projects is using a **Nix Flake**. This allows you to define a single configuration at the root of your workspace that provides specific development environments (shells) for each project.

## Workspace Structure

Organize your directory so that the Nix configuration sits at the top, and each demo project lives in its own subdirectory.

```text
react-internals-study/
├── flake.nix
├── project-1-tiny-react/
├── project-2-custom-renderer/
├── project-3-priority-scheduler/
└── project-4-hook-manager/
```

## The Flake Configuration

Create a `flake.nix` file in the root directory. This configuration creates four distinct development shells. While they all share a base of Node.js and TypeScript, separating them allows you to add project-specific system dependencies (like C++ build tools for a canvas-based renderer) without bloating the other projects.

```nix
{
  description = "React Internals Study Series";

  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    flake-utils.url = "github:numtide/flake-utils";
  };

  outputs = { self, nixpkgs, flake-utils }:
    flake-utils.lib.eachDefaultSystem (system:
      let
        pkgs = import nixpkgs { inherit system; };
        
        # Common tools for all React demo projects
        commonDeps = with pkgs; [
          nodejs_20
          nodePackages.typescript-language-server
          nodePackages.npm
        ];
      in
      {
        devShells = {
          # Project 1: Minimal engine (Standard JS/TS)
          tiny-react = pkgs.mkShell {
            name = "tiny-react-env";
            buildInputs = commonDeps;
            shellHook = "echo 'Welcome to Tiny-React Engine Env'";
          };

          # Project 2: Custom Renderer (May need build tools for native bindings)
          custom-renderer = pkgs.mkShell {
            name = "custom-renderer-env";
            buildInputs = commonDeps ++ [ pkgs.pkg-config pkgs.cmake ];
            shellHook = "echo 'Welcome to Custom Renderer Env'";
          };

          # Project 3: Scheduler (Focus on timing and performance)
          priority-scheduler = pkgs.mkShell {
            name = "scheduler-env";
            buildInputs = commonDeps;
            shellHook = "echo 'Welcome to Priority Scheduler Env'";
          };

          # Project 4: Hook Manager (Standard JS/TS)
          hook-manager = pkgs.mkShell {
            name = "hook-manager-env";
            buildInputs = commonDeps;
            shellHook = "echo 'Welcome to Hook Manager Env'";
          };
        };
      }
    );
}
```

## How to Use the Environments

Since you are using a Flake, you don't need to install Node.js globally on your system. You simply "enter" the environment for the project you are currently working on.

1.  **To work on Tiny-React:**
    ```bash
    cd project-1-tiny-react
    nix develop .#tiny-react
    ```
2.  **To work on the Custom Renderer:**
    ```bash
    cd project-2-custom-renderer
    nix develop .#custom-renderer
    ```

## Pro Tip: Automate with `direnv`

Entering the shell manually every time is tedious. To make this seamless, install `direnv` and create a `.envrc` file in each project folder.

In `project-1-tiny-react/.envrc`, add:
```bash
use flake .#tiny-react
```

Now, whenever you `cd` into that directory, Nix will automatically load the correct Node.js version and dependencies, and unload them when you leave the directory.

## Managing project-level dependencies

While Nix manages the **system-level** tools (Node, TypeScript, compilers), you should still use a `package.json` inside each project folder for the **library-level** dependencies. 

For example, in `project-2-custom-renderer/package.json`, you would run:
```bash
npm install react-reconciler
```
Nix ensures that the `npm` and `node` binaries used to install that package are identical across every machine that clones your repo, eliminating the "it works on my machine" problem.
